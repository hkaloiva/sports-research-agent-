# Web Access Architecture — Options Investigation

**Status: investigation only.** No provider has been chosen, no dependency
has been installed, and no implementation code has been written. This
document exists to inform a future decision, not to make one.

## Why this document exists

Everything built so far (Steps 1–7) runs *inside* this Claude Code
session and, where it touches the internet at all, does so through tools
(`WebSearch`, `WebFetch`) that belong to this development sandbox — not
to an application. Step 7 specifically found that `WebFetch` is blocked
entirely in this session, which made the gap concrete: **a standalone,
distributable Sports Research application needs its own legitimate
web-access mechanism, independent of Claude Code, Claude Chat, or this
sandbox.** This document surveys what that mechanism could realistically
be.

All pricing/tier/policy figures below come from web searches run while
writing this document (current as of this session). Provider pricing and
free-tier terms change often and have visibly changed even within 2026
(see [Limitations](#major-legal--technical-limitations)) — re-verify
against the provider's own current pricing page before implementing
anything.

## The one thing this whole investigation hinges on

**A search result is not source content.** A search API returns, at
most, a title, a URL, and a short indexed snippet — sometimes wrapped in
an AI-generated summary paragraph. None of that is the actual page. This
project already encodes that distinction structurally: Step 6's
`schema/search_result.schema.json` treats `snippet` as nullable and
never synthesizes one from a summary, and Step 7 refused to extract match
data from `WebSearch`'s synthesized answer text precisely because it's a
paraphrase, not a verified read of a specific page.

That distinction gets *harder*, not easier, once real search-API vendors
are involved, because several of them sell an "AI answer" feature
alongside raw results (Tavily's optional `include_answer`, and similar
features elsewhere) — a paragraph generated by *their* model from *their*
index. **That generated answer must never be fed to extraction as if it
were source content**, for the same reason `WebSearch`'s summary
couldn't be: it's a secondhand paraphrase, and using it would misattribute
invented wording to a URL that never carried it. The architecture
proposed below (see [Proposed architecture](#proposed-architecture))
makes this a structural property (two different types, two different
interfaces) rather than a rule someone has to remember.

## Legal / licensing considerations

- **Scraping case law has moved, but doesn't grant a blank check.**
  *hiQ Labs v. LinkedIn* (2022) established that scraping publicly
  available data isn't a CFAA violation on its own — but hiQ still lost
  on breach of LinkedIn's terms. *Meta v. Bright Data* (Jan 2024)
  reinforced this split: scraping public data without bypassing
  authentication isn't CFAA hacking, but a site's own Terms of Service
  remain independently enforceable as a contract-law matter. Practically:
  **respecting robots.txt and each site's ToS is not optional risk
  management** for anything shipped to other people, even where it isn't
  strictly a criminal-law question.
- This is the core reason to prefer a **hosted content-retrieval service**
  (Jina Reader, Firecrawl, Tavily extract) over a self-hosted scraper as
  the primary `ContentProvider`: those vendors carry their own
  relationship (and legal exposure) with the sites they fetch from,
  rather than putting that exposure on this application or its users.
- **Wikipedia/Wikimedia** content is under a CC BY-SA license — commercial
  use is explicitly permitted, provided attribution requirements are met
  and the API's fair-use/rate-limit policy (proper `User-Agent`,
  reasonable volume) is respected. This makes it an unusually strong,
  low-risk complement specifically for historical sports content, but
  it's one domain, not a general solution.
- **Bundling a single shared API key inside distributed software is not
  viable** — most of these providers' terms prohibit key-sharing/reselling
  access, and a shared key would also hit rate limits almost immediately
  across many users. See [Recommendations](#recommendations) for the
  practical alternative (bring-your-own-key).
- None of the above is legal advice. Provider ToS pages should be read in
  full, current form — not summarized from marketing/pricing pages —
  before a commercially distributed product ships, ideally with actual
  legal review given the "distributed to other people" requirement.

## Major legal / technical limitations

1. **Bing Search API is gone entirely** (retired Aug 11, 2025) — it isn't
   a fallback or an alternative to evaluate later, it simply cannot be
   used.
2. **Google Custom Search JSON API is closed to new customers** and fully
   shuts down Jan 1, 2027 — not viable for a new, longer-lived
   application even though it technically still works today for existing
   customers.
3. **Free tiers are volatile.** Brave removed its recurring free tier in
   early 2026 after offering one since 2023; ScraperAPI's free tier
   appears to have shrunk to a time-limited trial. A distributed
   application depending on end users' free-tier keys needs to handle
   "the free tier changed or disappeared" as a normal, expected failure
   mode — and pricing here should be re-verified at implementation time,
   not treated as fixed.
4. **Distribution forces a bring-your-own-key model.** Given the
   ToS/rate-limit realities above, each end user of a distributed
   application would need to obtain their own (typically free-tier) API
   key(s) — this is a real onboarding-friction cost of the "distributed
   to other people" requirement, not an implementation detail to solve
   later.
5. **Sports-API free tiers generally don't cover deep history** — the
   project's own target case ("Arsenal 2003/04") is exactly the kind of
   request football-data.org's free tier explicitly excludes. A
   `SportsDataProvider` should be treated as an accelerator for
   *well-covered recent data*, with the general search→fetch→extract path
   as the fallback for everything else — never the other way around.
6. **Rendering-heavy sites cost more.** Where a page needs JavaScript
   execution to show its content (some modern stats sites), the
   content-retrieval options above that handle it (Firecrawl, ScrapingBee,
   Jina) charge more credits for that mode — a real cost variable that
   depends on which specific sources end up used most.

## Recommendations

### 1. Best option for the prototype
**Tavily**, for both search and content retrieval. One account, one key,
a generous no-card-required free tier (1,000 credits/mo), and its
`/extract` endpoint is a genuine, purpose-built `ContentProvider` — not a
repurposed scraping service. This minimizes prototype integration work
while still respecting the search-vs-content type separation
architecturally (see below).

### 2. Best option for a distributed application
No single answer — this is a two-part decision because of the
bring-your-own-key constraint:
- **Search:** Brave Search API or Tavily — both have straightforward,
  self-serve signup with no approval process, which matters when *end
  users*, not just the developer, need to obtain a key.
- **Content:** Jina AI Reader — its no-key basic tier (20 req/min) means
  many end users may need **zero additional signup** for content
  retrieval at light usage, which meaningfully lowers onboarding
  friction compared to requiring a second paid-service key.
- Serper/SerpApi were not recommended here specifically because they
  resell Google's own results — workable and widely used, but a model
  whose redistribution terms deserve a closer read than this survey gives
  them before committing a distributed product to it.

### 3. Best low-cost option
- **Search:** Tavily's free tier (1,000 credits/mo recurring, no card) for
  low volume; Serper's paid tiers ($0.30–$1.00/1,000) if free-tier volume
  is exceeded and cost-per-query matters most.
- **Content:** Jina AI Reader — effectively free at prototype-to-light-
  production scale.
- **Sports data:** football-data.org and TheSportsDB are genuinely free
  "forever" per their own stated policy, though football-data's
  current-season-only free limit is a real constraint for this project's
  historical focus specifically.

### 4. One provider, or separate `SearchProvider`/`ContentProvider` interfaces?
**Separate interfaces, potentially one provider underneath.** Define
`SearchProvider` and `ContentProvider` as two distinct abstractions in
code — this is what makes "a search result is not source content" a type
system fact instead of a convention someone can forget. It's fine, even
good for the prototype, for a single vendor (Tavily) to implement *both*
interfaces under one account — but the interfaces themselves stay
separate so either half can be swapped independently later (e.g. keep
Tavily for search, move to Jina for content once cost matters more)
without touching the other.

## Proposed architecture

Not implemented — this describes what already exists as an abstraction
in this codebase, and where the missing piece would slot in.

```
ResearchRequest  (Step 4 — unchanged)
      │
      ▼
SearchPlan       (Step 5's planner.py — unchanged)
      │
      ▼
┌─────────────────────┐        ┌──────────────────────┐
│   SearchProvider     │        │   ContentProvider      │
│  search(query)        │        │  fetch(url)            │
│  -> list[SearchResult]│        │  -> SourceContent      │
└─────────────────────┘        └──────────────────────┘
      │  (title, url, snippet?)         │  (actual page text)
      └───────────────┬─────────────────┘
                       ▼
              ResearchEngine
        (orchestrates: plan the search,
         run it, pick candidate source(s),
         fetch their content, extract,
         validate, optionally cross-check)
                       │
        ┌──────────────┼───────────────────┐
        ▼              ▼                   ▼
  extractor.py    validation.py     SportsDataProvider (optional)
  (Step 7 —        (Step 2 —         get_season_results(...)
   unchanged)        unchanged)      -> near-canonical records,
                                      bypassing search+fetch+extract
                                      for well-covered leagues/seasons
```

- **`SearchProvider`** is already the shape of `search.py`'s pluggable
  `backend: Callable[[str], list[dict]]` from Step 6 — a real
  implementation (`TavilySearchProvider`, `BraveSearchProvider`, ...)
  would satisfy that same contract; `SearchResult`
  (`schema/search_result.schema.json`) doesn't need to change.
- **`ContentProvider`** is a genuinely new piece. It sits exactly where
  Step 7's `extractor.py` currently expects pre-fetched raw text to
  already exist — `extract_records()` wouldn't change; something upstream
  of it would now call a real `ContentProvider.fetch(url)` instead of
  reading a saved fixture file.
- **`SportsDataProvider`** is optional and additive: a `ResearchEngine`
  can check it first for competitions/seasons it covers, and fall back to
  `SearchProvider` + `ContentProvider` + `extractor.py` otherwise — never
  the reverse, and never assumed to be the sole source per this step's
  brief.
- **`ResearchEngine`** is the only new orchestration layer; every stage it
  calls already exists (`planner.py`, `search.py`, `extractor.py`,
  `validation.py`) except the two provider interfaces themselves.

## What the eventual end user would need

Depends on which recommendation is chosen, but generally **1–3 free
self-serve API keys**, none requiring an approval or sales process:

- 1 key for the chosen `SearchProvider` (e.g. Tavily or Brave)
- 0–1 key for the `ContentProvider` (0 if Jina's no-key tier is used at
  light volume; 1 if using Tavily's extract or a paid content service)
- 0–1 key for an optional `SportsDataProvider` (e.g. API-Football), only
  if that integration is built

## Estimated prototype cost

**$0/month is achievable** for prototype-scale development:

- Tavily alone (search + content): free tier, 1,000 credits/mo, no card.
- Or Brave ($5 one-time credit ≈ 1,000 queries) + Jina Reader (free,
  no-key tier): effectively $0–5 total, not recurring.
- Sports-API free tiers (football-data.org, TheSportsDB): $0/month.

This is a *current* snapshot, not a guarantee — Brave's own 2026 removal
of its long-standing free plan is a concrete example of exactly this kind
of change happening with no warning.
